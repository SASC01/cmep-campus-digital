# ARCHITECTURE-ESSENTIALS

> Solo decisiones y reglas. Detalle y justificación en `ARCHITECTURE.md`; producto en `PRD.md`.
> Si algo aquí contradice a otro documento, **manda este** y se avisa al humano.

## Qué es
**CMEP Campus Digital.** Plataforma educativa web, una sola institución, 3 roles (`estudiante`, `maestro`, `admin`). **Fase experimental**, ~1,500 usuarios previstos; la arquitectura se diseña para 2,000 simultáneos. Sin integraciones con Google.

## Proveedores
- **Sin AWS.** Ni servicios ni librerías. La regla aplica a servicios y a librerías que nuestro código importa o ejecuta; las dependencias transitivas de herramientas de desarrollo (por ejemplo, del CLI de Prisma) se reportan, pero no bloquean.
- Aprobados: **DigitalOcean** (Droplet), **Cloudflare** (DNS, Pages, R2), **Resend** (correo) y, para clases en vivo, **un proveedor alojado de BigBlueButton** que el humano aprueba por escrito al contratarlo, también para el plan gratuito de desarrollo (candidato sin verificar; D-33). LiveKit Cloud salió de la lista el 2026-11-11. Nada más sin aprobación explícita del humano.
- Todo proveedor debe poder cambiarse por configuración. El núcleo (API, worker, PostgreSQL) corre igual en local, en el Droplet o en un servidor propio.
- **Correo solo con Resend, por API HTTPS, y solo desde `adapters/notifier`.** Nada de SMTP ni de otras librerías de correo. Fuera de `prod` jamás sale un correo real.

## Stack
- **Frontend:** React + Vite + TypeScript · Tailwind (tokens propios) · shadcn/ui reestilizado · lucide-react · sonner · React Router · TanStack Query · FullCalendar → **Cloudflare Pages** (`campus.<dominio>`)
- **Backend:** Node.js LTS + Fastify + TypeScript · zod · monolito modular → **Droplet** con Docker Compose (`api.<dominio>`, tras el proxy de Cloudflare y Caddy)
- **Datos:** PostgreSQL 17 (`pg_trgm`, `unaccent`) · Prisma
- **Auth:** propia — argon2id + JWT (`jose`) + token de refresco rotativo en cookie `HttpOnly`
- **Cola y trabajos diferidos:** pg-boss
- **Archivos:** protocolo S3 con cliente `minio` → **R2** en `prod`, **MinIO** en `dev` (imágenes desde `quay.io`, sin mantenimiento; reemplazable por cualquier almacén S3 vía `STORAGE_*`)
- **Video:** BigBlueButton por su API con un proveedor alojado (D-33), detrás de `adapters/live` · sin servidor local en `dev`: plan gratuito del proveedor y, en las pruebas, un doble
- **Operación:** pino · monitoreo de DigitalOcean · `pg_dump` cifrado hacia R2 · GitHub Actions construye y publica las imágenes
- **Pruebas:** Vitest. Backend: unitarias de `core/` y `config/`, e integración contra un PostgreSQL desechable por corrida con Testcontainers (imagen de `infra/`, `prisma migrate deploy` al iniciar); nunca `campus_dev`, una base compartida ni `prod`. Frontend: jsdom + Testing Library, sin API ni infra

## Capas del backend
```
handlers → middleware → core → (interfaces) ← adapters → librerías de infraestructura
```
- `core/`: lógica pura. Sin I/O ni librerías de infraestructura.
- `config/`: validación de las variables de entorno con zod y opciones del logger. No es `core/` ni `adapters/`.
- `adapters/`: **único** lugar que importa `@prisma/client`, `@prisma/adapter-pg`, `pg`, el cliente generado por Prisma (`adapters/db/generated/`, no versionado), `pg-boss`, `minio`, `resend`, `argon2`, `jose` o `livekit-server-sdk`. Módulos: `db`, `auth`, `storage`, `notifier`, `queue` (cola y trabajos diferidos de pg-boss, con su única instancia; no hay un módulo `scheduler` aparte, TAREAS-01), `live`. La exportación de calificaciones a .xlsx (CALIFICACIONES-02) no se escribe en el backend: la API devuelve JSON por ventanas y el navegador arma el archivo con un escritor propio (`frontend/src/lib/xlsx.ts`), sin dependencia nueva ni servicio externo (R-01 de DOCS-04 y DH-01 de CALIFICACIONES-02, decisiones del humano).
- `handlers/`: delgados. Un plugin de Fastify por dominio: `auth`, `usuarios`, `clases`, `tareas`, `calificaciones`, `archivos`, `notificaciones`, `calendario`, `envivo`, `publico`, `admin`.
- `workers/`: consumidores de la cola. `api` y `worker` son la misma imagen con distinto arranque.
- `shared/`: tipos y esquemas zod comunes. `infra/`: compose, Caddyfile, respaldos, despliegue.

## Autenticación
- Contraseñas con argon2id, mínimo 10 caracteres. Nunca en logs.
- Token de acceso: JWT de 15 min, solo `sub`, en memoria del navegador. **Nunca en `localStorage`.**
- Token de refresco: aleatorio, cookie `HttpOnly; Secure; SameSite=Strict`, guardado **solo como hash**, 30 días, rotación en cada uso, reutilización ⇒ se revocan todas las sesiones.
- Login: 5 intentos / 15 min por IP + correo. Mismo mensaje para usuario inexistente y contraseña incorrecta.
- El correo es el identificador de acceso y **no se verifica**: puede estar mal escrito.
- Registro público: solo estudiantes. Maestros: los da de alta el admin, por invitación individual o masiva (enlace de un solo uso por correo, 72 h; al activarlo, el maestro ve y puede corregir su nombre), o se registran con un enlace de registro que genera el admin (token aleatorio mostrado una sola vez y guardado solo como hash; vigencia de 1 a 30 días, 7 por defecto; revocable; el admin ve quién se registró con cada enlace; D-04). Admin: `npm run seed:admin`, cuenta única, sin endpoint.
- **Recuperación por correo:** enlace de un solo uso, 30 min, guardado solo como hash (`tokens_cuenta`); misma respuesta y mismo tiempo exista o no el correo; 3 solicitudes por hora; al usarlo se revocan las sesiones. La API encola siempre y el worker resuelve la cuenta (no hay recuperación para el admin); límite de 3 por hora por IP + correo en la API y por cuenta en el worker. El token del enlace se deriva de su id con una clave del servidor y viaja en el fragmento de la URL.
- **Respaldo por el admin:** contraseña temporal aleatoria mostrada **una sola vez**, guardada solo como hash, activa `debe_cambiar_contrasena` y revoca sesiones. El cambio obligatorio pide solo la contraseña nueva y su confirmación, no la temporal, y exige una sesión viva del mismo usuario (cookie de refresco); un futuro cambio voluntario desde el perfil sí pedirá la actual. El admin puede corregir un correo. La del admin: `npm run reset:admin`.

## Autorización (orden fijo, siempre en backend)
1. `authenticate` → 2. `withProfile` → 3. `withPasswordGate` → 4. `withAccess` → 5. `requireRole` → 6. `requireMembership` / `requireOwnership` → 7. handler

- Rol, restricción y banderas se leen de la base en **cada** petición; no van en el token.
- `debe_cambiar_contrasena`: solo pasa `POST /auth/cambiar-contrasena`.
- Alumno restringido: solo `GET /me` y `GET /me/estado-pago` (y `POST /auth/cambiar-contrasena` si tiene un cambio pendiente). Sin entradas a clases en vivo, archivos ni grabaciones.
- Estado de pago ajeno: solo admin, o maestro de una clase del alumno. Para estudiantes el campo **se omite**.
- `requireMembership`: estudiante inscrito, cualquier maestro de la clase o el admin; `requireOwnership`: cualquier maestro de la clase (de uno a dos, en `maestros_de_clase`) o el admin; siempre sobre `:claseId`, con la misma respuesta para una clase inexistente y una ajena. El admin pasa el sexto paso en cualquier clase que exista, pero solo en las rutas cuyos `roles` lo nombran de forma explícita: en una ruta sin `roles`, el sexto paso lo niega (cerrado por defecto). La guarda de `:claseId` no tiene excepciones (CLASES-02).
- Una guarda `onRoute` no deja arrancar la API si una ruta no pública, con cualquier URL, no empieza por la cadena completa o tiene un parámetro o un comodín en sus dos primeros segmentos (CHORE-02).
- Clase archivada (ADMIN-01; P-08 de DOCS-04, decisión del humano, 2026-10-26): se resuelve en el sexto paso de la cadena, no en los handlers. Cada ruta con `:claseId` declara en `protegido()` qué hace con una archivada (`enClaseArchivada`, que decide `evaluarClaseArchivada` de `core/clases/archivada.ts`): `"lectura"` deja pasar a los maestros de la clase y al admin y responde `409` al alumno; `"lectura-del-alumno"` (el detalle de la clase y "Mis calificaciones") y `"gestion"` (archivar, restaurar, conteo de borrado, borrar y duplicar; solo con `roles: ["admin"]`) dejan pasar a los tres roles que la ruta admite. Sin declararla, la ruta queda cerrada: `409 CLASE_ARCHIVADA` para todos, también el admin (cerrado por defecto; toda escritura, el código de invitación, el buscador de candidatos y asignar o quitar maestros). Una clase inexistente o ajena sigue respondiendo `403 SIN_ACCESO_A_LA_CLASE` antes del `409`, así no se revela que está archivada. `protegido()` no deja arrancar la API si la opción viene sin `pertenencia`, o si es `"gestion"` sin `roles: ["admin"]`. Solo lectura para todos: el maestro consulta sus clases archivadas sin escribir; el alumno, solo el detalle y sus calificaciones ("Clases anteriores"); el admin las lee y las gestiona (restaurar, duplicar y borrar).

## Reglas de datos
- Prisma **solo** en `adapters/db`.
- **Sin N+1:** ninguna consulta dentro de un ciclo.
- Toda consulta filtra por columna indexada; toda lista se pagina (máx. 100).
- SQL crudo solo parametrizado. El único SQL con texto no literal que pasa por Prisma es el de pg-boss al encolar dentro de una transacción (`ejecutorSqlDe` en `adapters/db`, único `$queryRawUnsafe`): todos sus datos viajan como parámetros y el texto solo interpola el esquema, la tabla y el nombre de la cola (constantes del código).
- Escrituras compuestas en **transacción**, incluido el encolado del evento.
- Transacciones que crean, rotan o revocan sesiones en bloque, cambian la contraseña o escriben enlaces de un usuario existente: primero su fila de `usuarios` (`FOR SHARE` para crear o rotar su sesión; `FOR NO KEY UPDATE` para lo demás), en READ COMMITTED. Protocolo en `backend/src/adapters/README.md`.
- Toda transacción se abre con `enTransaccion` (`adapters/db`). Si expira esperando un bloqueo o una conexión (`P2028`), responde `503 SERVICIO_OCUPADO`, nunca `500`.
- **Edición concurrente** (ENTREGAS-01): llevan `version` (entero, desde 0, sube en cada cambio) las filas que se editan con un formulario que reemplaza lo guardado y las decisiones que alguien toma sobre lo que vio: hoy `tareas` (editar la exige; mover de tema también la sube), `entregas` (entregar, anular y calificar la suben; calificar la exige: si el alumno anuló o volvió a entregar, u otra persona calificó, `409 ENTREGA_MODIFICADA`) y `publicaciones` de los recursos (editar la exige; mover un recurso también la sube; `409 RECURSO_MODIFICADO`; CLASES-03). Calificar envía además los puntos de la tarea que vio (`puntosDeLaTarea`): si ya no son los de la tarea bloqueada, o la rúbrica cambió, `409 RUBRICA_MODIFICADA`; no usa `tareas.version`, que también sube al mover de tema (CALIFICACIONES-01). La petición envía la versión que vio; si no coincide con la de la fila ya bloqueada, `409` sin escribir nada. `actualizado_en` no sirve de precondición. Tras el `409`, el formulario de la tarea avisa, descarta lo escrito y recarga la versión actual, como el editor de categorías (decisión del humano, 2026-10-11). Tras un `409` al calificar (`ENTREGA_MODIFICADA`, `RUBRICA_MODIFICADA` o `ENTREGA_NO_CALIFICABLE`), el panel de calificación avisa, descarta lo escrito y recarga la entrega y, con `RUBRICA_MODIFICADA` o `ENTREGA_NO_CALIFICABLE`, también la tarea, como el formulario de la tarea; si la recarga falla, conserva lo escrito y la versión que vio (CALIFICACIONES-01). Excepciones ya decididas, sin versión: las categorías se guardan en bloque y, tras un `409` o un `404`, el editor descarta y recarga (decisión del humano, 2026-10-11); los temas se renombran y ordenan sin versión, porque no hay texto largo que perder, y el orden se renueva tras `ORDEN_DESACTUALIZADO`.
- Una lectura de varias sentencias (Prisma resuelve cada relación anidada con otra sentencia) cuya respuesta exige una relación obligatoria o una cardinalidad mínima, o que comprueba la fila del cursor antes de leer la página, se hace en una sola instantánea: `enTransaccion` con `instantaneaUnica` (REPEATABLE READ, solo lecturas). Las transacciones que escriben siguen en READ COMMITTED (FIX-CLASES).
- **Cursor con posición** (ADMIN-01; opción A de T-02 de 01a, decisión del humano, 2026-11-04): una lista paginada por cursor cuya clave de orden puede cambiar lleva, junto con `cursor` (el id), la posición que esa clave tenía en la fila del cursor cuando el servidor la entregó: `cursorArchivadaEn` en `GET /clases/anteriores` y `GET /admin/clases?estado=archivadas`, y `cursorNombre` en `GET /admin/usuarios`; la respuesta trae `siguienteCursorArchivadaEn` o `siguienteCursorNombre`. El servidor lee la fila del cursor por su PK y compara su clave actual con la posición como texto, literalmente, sin interpretarla; si no coinciden, si falta una de las dos o si la fila no cumple el filtro, responde `400 VALIDACION` "cursor: no es válido", el mismo cuerpo que cualquier cursor inválido. Protege solo la fila del cursor: si otra fila de la lista se mueve entre dos páginas, la siguiente responde `200` con esa fila saltada o repetida (R-19, riesgo aceptado por el humano); la interfaz descarta las repetidas por `id` (`unirPaginasSinRepetidas`) y la saltada aparece al volver a abrir la lista. Las listas cuya clave no cambia (la del admin sin `estado` o con `activas`, inscritas, impartidas, movimientos de inscripción) no llevan posición.
- Promedios, gradebook, alumnos en riesgo y KPIs: **consultas agregadas**, no contadores guardados.
- Todo cambio de esquema es una migración de Prisma, **compatible hacia atrás** (frontend y backend se despliegan por separado).
- Fechas `timestamptz` en UTC; ISO 8601 en la API.
- Tablas y columnas en `snake_case` español; `camelCase` en TypeScript vía `@map`. Llaves UUID.
- Búsqueda de alumnos: `nombre_busqueda` se normaliza en `core/` al escribir (sin acentos, minúsculas, espacios colapsados) y se busca con `LIKE` y el índice GIN de trigramas sobre esa columna; el término pasa por la misma normalización, definida una sola vez en `shared/`, y escapa los comodines. Mide de 3 a 120 caracteres ya normalizados, con un tope de 1000 en crudo. `unaccent` no se usa en las consultas. Frontend: espera de 300 ms.

Restricciones clave: `email` único · un solo `rol = 'admin'` (índice único parcial) · `maestros_de_clase (clase_id, maestro_id)` PK, de uno a dos por clase, validado en `core/` dentro de la transacción, con la fila de la clase bloqueada (CLASES-02) · `entregas (tarea_id, alumno_id)` único · `notificaciones (usuario_id, evento_id)` único · `comentarios` con exactamente un contexto: `publicacion_id` (muro y recursos), `entrega_id` (hilo privado; ENTREGAS-01) o `duda_id` (respuestas de una duda; CLASES-03) · `archivos`: confirmado si y solo si tiene exactamente un contexto (`publicacion_id` o `entrega_id`; los `pendiente` y `descartado`, ninguno; `clase_id` autoriza mientras tanto) · `entregas`: una fila por alumno y tarea, creada al primer uso (entregar, comentar o calificar); `asignado` sin `fecha_entrega`, `entregado` con ella, y `calificado` con `calificacion` y `fecha_calificacion`, con o sin `fecha_entrega` (sin ella cuando se calificó a quien no entregó); sin `fecha_entrega` no hay retraso ni enlaces. "Entregó" es tener `fecha_entrega`, no el estado (ENTREGAS-01; CALIFICACIONES-01) · `puntajes_rubrica (entrega_id, criterio_id)` PK, el desglose de una calificación con rúbrica; su FK a `criterios_rubrica` es `NO ACTION DEFERRABLE INITIALLY DEFERRED` (se comprueba al confirmar) y está escrita a mano en la migración, porque Prisma no la expresa (CALIFICACIONES-01) · `categorias.peso` de 1 a 100, con la suma de 100 por clase validada en `core/` con la fila de la clase bloqueada · `publicaciones.tema_id` con `ON DELETE SET NULL`; un anuncio no lleva tema (TAREAS-01) · una tarea es una publicación de tipo `tarea` con su fila 1:1 en `tareas` (mismo id; TAREAS-01) · `publicaciones.bloque` solo en materiales, escrito al publicar con el rol del autor; un nulo (solo por compatibilidad) se lee con el bloque del rol del autor (CLASES-03).

## Asíncrono y notificaciones
- La API guarda y encola **en la misma transacción**, y responde. **Nunca** crea notificaciones en la petición.
- Todo aviso y todo correo sale por `adapters/notifier`: `avisar(destinatarios, aviso)` y `correoDeCuenta(...)`. Nadie más escribe en `notificaciones` ni llama a Resend.
- **Aviso = notificación in-app siempre + correo solo si ese tipo está activado** en `configuracion` (todos apagados por defecto; los enciende el admin).
- **Correos de cuenta** (recuperación, invitación de maestro): siempre activos, solo por correo, con prioridad en la cola. La invitación masiva se rechaza completa si rebasa el cupo `INVITACIONES_LIMITE_DIARIO` (80 invitaciones en las últimas 24 h; Resend gratuito: 100 correos por día UTC) y encola un trabajo por maestro en su misma transacción; el worker deja al menos 250 ms entre dos intentos de envío.
- Un correo por destinatario, con límite de ritmo. Canal `registro` en `dev` y pruebas.
- Idempotencia por `eventId`. 3 reintentos con espera exponencial; después, cola de fallidos vigilada.
- Eventos: `PUBLICACION_CREADA` · `MATERIAL_CREADO` · `TAREA_CREADA` · `ENTREGA_REALIZADA` · `CALIFICACION_PUBLICADA` · `COMENTARIO_CREADO` · `RECORDATORIO_24H` · `CLASE_POR_COMENZAR` · `CORREO_DE_CUENTA` · `ENVIAR_CORREO` · `GRABACION_LISTA` · `LIMPIEZA_DIARIA` · `RESPALDO_DIARIO` · `COPIAR_OBJETOS` · `BORRAR_OBJETOS` (ADMIN-01; abajo, "Archivos"). `ENTREGA_REALIZADA` lleva `{ entregaId, tareaId, claseId, version }` con un id nuevo por entrega; `COMENTARIO_CREADO` sirve al muro y al hilo privado (ENTREGAS-01). `CALIFICACION_PUBLICADA` lleva `{ entregaId, tareaId, claseId, version }` con un id nuevo por publicación (también al recalificar) y cubre el comentario de la devolución, que no encola `COMENTARIO_CREADO` (CALIFICACIONES-01). DOCS-04 no agrega eventos: los avisos de "Dudas" y del foro los decide NOTIFICACIONES (P-11, decisión del humano, 2026-10-26); los recursos siguen con `MATERIAL_CREADO` y los anuncios de "Avisos" con `PUBLICACION_CREADA`.
- Frontend: sondeo cada 60 s + al enfocar la pestaña. Sin WebSockets. Contador = `COUNT` sobre índice parcial de no leídas. Retención de 90 días.

## Trabajos diferidos
- Uno por tarea (`fecha_limite − 24 h`) y uno por clase en vivo (`fecha_inicio − 15 min`). Desde FORO-01, uno por actividad con fecha límite: tarea o foro (DOCS-04).
- Guardar `trabajo_id`. **Editar o borrar la fecha ⇒ cancelar y recrear, en la misma transacción.**

## Archivos
- Subida y descarga con URL prefirmada de 5 min. Los archivos **nunca** pasan por Node ni por el Droplet.
- Registro `pendiente` → `confirmado`; los pendientes de más de 24 h se borran.
- Buckets: `campus-privado` (`materiales/` · `entregas/` · `grabaciones/`) · `campus-publico` (`anuncios/`) · `campus-respaldos` (solo en `prod`; en `dev` MinIO crea únicamente los dos primeros).
- Tokens de mínimo privilegio: aplicación y respaldos. Si copiar las grabaciones necesita una credencial propia, la define ENVIVO.
- Cambiar de almacén = cambiar `STORAGE_ENDPOINT`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`.
- Materiales, anuncios y adjuntos de tareas: solo los sube un maestro de la clase o el admin (CLASES-02); 25 MB por archivo, 5 por publicación o tarea; PDF, imágenes (sin SVG), Office y texto plano. La confirmación compara el objeto real con lo declarado, dentro de la transacción de la publicación. Vista previa solo de imágenes. La limpieza borra también el objeto de los pendientes vencidos y de los descartados.
- Entregas (ENTREGAS-01): el alumno sube los archivos de su entrega por su propia ruta (`…/tareas/:tareaId/entrega/archivos`, solo mientras puede entregar), con clave `entregas/{tareaId}/{alumnoId}/{archivoId}`; mismos tipos, 25 MB por archivo y 5 por entrega, más hasta 5 enlaces `http`/`https`. Un archivo de entrega solo se descarga por sus rutas (el alumno, los suyos; los maestros de la clase y el admin, los de sus alumnos inscritos); la descarga de la clase solo sirve archivos de publicaciones, y la confirmación de una publicación o de una entrega exige el prefijo de su clave. Anular pasa los archivos a `descartado`.
- Previsto (DOCS-04): los recursos (CLASES-03) usan los archivos de los materiales, sin cambio; los adjuntos del planteamiento de un foro, los de una tarea (FORO-01). La exportación .xlsx (CALIFICACIONES-02) y los objetos de una clase borrada o duplicada (ADMIN-01) siguen esta sección: nada pasa por Node en una petición.
- Duplicar y borrar una clase (ADMIN-01; DH-03 y DH-04): **objetos propios, copiados del lado del almacén.** Duplicar crea, en su transacción, las filas de `archivos` de la copia (`confirmado`, clave `materiales/{claseNueva}/{archivoNuevo}`, `copia_de` = el original) y encola `COPIAR_OBJETOS` (hasta 100 archivos por trabajo); el worker copia cada objeto con `copyObject` y pone `copia_de` en nulo, sin consultas dentro del ciclo; si el original ya no existe, o el trabajo llega a su cola de fallidos (`COPIAR_OBJETOS_FALLIDO`), la copia pasa a `descartado`. Mientras `copia_de` no es nulo, la descarga de la clase responde `409 ARCHIVO_EN_COPIA`, ninguna de las dos clases se borra y la copia no se vuelve a duplicar (`409 CLASE_CON_COPIAS_EN_CURSO`). Descartar un archivo de publicación (borrar la publicación, quitar un adjunto al editar un recurso) pone también `copia_de` en nulo. Borrar definitivamente lee las claves de todos los archivos de la clase, en cualquier estado, y encola `BORRAR_OBJETOS` (hasta 1000 claves por trabajo) diferido 10 minutos, para alcanzar también el objeto de una subida firmada antes de archivar; el worker borra con `removeObjects`, es idempotente y deja que un error del almacén se reintente. La exportación no deja archivo en el servidor ni en el almacén: la API devuelve los datos en JSON y el navegador arma el .xlsx, sin cola (R-01 de DOCS-04, decisión del humano, 2026-10-26).
- Sin las tres `STORAGE_*` de acceso, la API arranca y los archivos responden 503; en `production` son obligatorias (API y worker). Firmar es local: la región es fija (`STORAGE_REGION`).

## Clases en vivo

Cambiar de proveedor o pasar a un servidor propio es cambiar la URL y el secreto de la API (`BBB_URL` y `BBB_SECRET`, previstos). El secreto solo en el `.env` del backend. Todo detrás de `adapters/live`. Zoom queda como alternativa registrada.

El aviso de grabación lista (firma verificada) encola `GRABACION_LISTA` y se conecta en DEPLOY, porque necesita una URL pública; hasta entonces, las grabaciones se recuperan por sondeo.
- **Abierto, lo cierra el plan de ENVIVO con el humano** (PRD, preguntas 18 a 22): pestaña nueva o aula embebida; grabación automática o controlada por el maestro (RF-41); modo webinar o dar la palabra; cupo por sala y qué ve el alumno con la sala llena; para qué son las salas del admin y quién entra; las preguntas de clases vinculadas; y cómo llega una grabación a nuestro almacenamiento: si cabe en la regla 6 de `AGENTS.md` (los archivos no pasan por Node) o necesita una excepción, que decide el humano.

## Reglas de negocio que tocan código
- Estado de pago: `Deudor` / `Al corriente`. Por defecto `Al corriente`. Manual, solo admin. Guarda fecha de cambio. **No bloquea nada por sí solo.**
- Restricción de acceso: independiente del estado de pago. Solo admin, solo estudiantes, efecto inmediato, reversible.
- Cuentas (ADMIN-01; P-01 a′, decisión del humano, 2026-11-04): la baja desactiva la cuenta y es reversible («Reactivar»): `activo = false`, revoca sus sesiones y sus enlaces de cuenta vivos y conserva todos sus datos; reactivar no restaura nada revocado. La cuenta de administración no se da de baja (`409 CUENTA_DE_ADMINISTRACION`). Un maestro asignado a alguna clase **activa** no se da de baja (`409 MAESTRO_CON_CLASES`, con el número de clases): primero se le quita de ellas. En sus clases archivadas se queda, y las respuestas que listan maestros lo marcan con `cuentaDesactivada: true` (la interfaz muestra «Cuenta desactivada»); no hay gestión de maestros en una archivada. Asignar, crear y duplicar toman las filas de los maestros `FOR SHARE` y vuelven a comprobar `activo` (`404 MAESTRO_NO_ENCONTRADO` con una baja en vuelo). **Cómo se lee RN-06** ("una clase nunca queda sin maestro"): la clase siempre tiene de uno a dos maestros asignados, aunque alguno pueda estar dado de baja. Una clase activa puede quedar solo con maestros dados de baja por dos vías, las dos aceptadas por el humano: restaurar una clase cuyos maestros están todos dados de baja (N-14, 2026-11-04) y quitar al único maestro activo de una clase que tiene otro dado de baja (OA-01e-r1-1, "Aceptarla y anotarla", 2026-11-09). Se resuelve asignando un maestro activo, porque la clase ya es activa. Alta de alumno por el admin: nombre y correo, con una contraseña temporal mostrada una sola vez y el cambio obligatorio, sin correo (`409 CORREO_EN_USO` si el correo ya existe); los maestros se siguen dando de alta por invitación o enlace. Restringir el acceso revoca las sesiones del alumno; el motivo es opcional y restablecer lo borra. El estado de pago se cambia desde la fila o por lote, de 1 a 100 alumnos por petición: si un id no es de un alumno, falla todo el lote sin escribir; la fecha de cambio solo se actualiza en las filas cuyo estado cambia. Cambiar el estado de pago no revoca sesiones.
- Calificación (RF-36, RN-05; CALIFICACIONES-01): un maestro de la clase califica una entrega con la rúbrica (la suma de los puntos por criterio, escalada a los puntos de la tarea y redondeada a centésimas) o, sin rúbrica, con una calificación directa, con hasta 2 decimales. Publicar es devolver: el alumno la ve en cuanto se guarda, y el comentario opcional de la devolución va al hilo privado de la entrega, sin aviso propio (P-01 y P-02). Recalificar vuelve a publicar. A quien no entregó solo se le califica con la entrega cerrada, es decir, con la fecha límite vencida en una tarea que no acepta entregas con retraso (P-03 c′): la fila queda `calificado` sin `fecha_entrega`, el alumno ya no entrega ni anula, y no cuenta entre los que entregaron. Una tarea con alguna entrega calificada no cambia sus puntos ni su rúbrica (`409 TAREA_CON_CALIFICACIONES`), y una rúbrica idéntica nunca se reemplaza (P-04). El admin lee las calificaciones y no califica (S-01). Calificación general: por categorías ponderadas y, dentro de cada una, por puntos (P-05); las categorías sin tareas calificadas no cuentan y su peso se reparte; las tareas sin calificar no cuentan; las entregas con retraso cuentan igual. Desde FORO-01, el foro es una actividad calificable más: se califica por alumno con las mismas reglas y pondera en su categoría (DOCS-04).
- Categorías ponderadas (RF-32; P-01 de TAREAS-01): hasta 10 por clase, sin nombres repetidos (misma comparación que los temas), con pesos enteros de 1 a 100 que suman 100; se guardan en bloque y las gestionan los maestros de la clase y el admin. Una clase sin categorías califica por puntos; con categorías, toda tarea nueva o editada lleva una, y una tarea "Sin categoría" no cuenta en la calificación general hasta asignarle una. No se quita una categoría que tiene tareas.
- Alumno en riesgo: promedio < 70 % o ≥ 3 tareas vencidas sin entregar. Los umbrales son constantes de `core/` hasta que exista la configuración (RF-56), y el promedio que se compara es el redondeado que se muestra. "Vencidas sin entregar" son las tareas de la clase con la fecha límite pasada y sin entrega `entregado` ni `calificado` del alumno: una calificada sin entrega no cuenta, porque su calificación ya pesa en el promedio. Cuentan también las que vencieron antes de que el alumno se inscribiera, como en "Trabajo de clase" (S-04) (CALIFICACIONES-01). Desde FORO-01 cuentan las actividades: un foro vencido sin participación principal del alumno es una vencida sin entregar (DOCS-04).
- Entregas (RF-14, RF-15, RF-24, RF-44; ENTREGAS-01): el alumno entrega una vez, con archivos y enlaces o, si la tarea no requiere adjuntos (`requiere_adjuntos`, lo decide el maestro), con "Marcar como completada"; anula y vuelve a entregar mientras no esté calificada. Tarde es después de la fecha límite: si la tarea acepta tardías, la entrega se marca `con_retraso` al entregarla; si no, se cierra en la fecha límite y ya no se entrega ni se anula. El cierre se calcula en cada acción con la tarea vigente: mover la fecha límite o aceptar tardías la reabre. Borrar una tarea con entregas (S-06, decisión del humano del 2026-10-11): un maestro no la borra (`409 TAREA_CON_ENTREGAS` con el conteo; lo pide a administración); el admin sí, con una confirmación explícita (`?confirmar=entregas`), en cascada e irreversible: se lleva las entregas, sus archivos y los hilos privados. Cuentan las entregas `entregado` y `calificado`. Hilo privado (RF-16; ENTREGAS-01): uno por alumno y tarea, entre el alumno y los maestros de la clase; el admin lo lee y no escribe; en esta fase sus comentarios no se borran ni se editan.
- Temas (RF-43; P-03 de CLASES-01 y P-02 de TAREAS-01): organizan las tareas y los materiales de una clase, con nombre y orden (hasta 30 por clase, sin nombres repetidos: se comparan con `claveDeNombre` de `shared/src/tareas.ts`, sin distinguir mayúsculas, acentos, caracteres invisibles ni formas de compatibilidad). Un elemento puede quedar "Sin tema"; dentro de un tema van del más reciente al más antiguo; borrar un tema pasa sus elementos a "Sin tema". Los gestionan los maestros de la clase y el admin; mover un elemento de tema organiza la clase y no cuenta como editarlo. El alumno ve "Trabajo de clase" agrupado y de solo lectura, y el muro sigue cronológico. Son independientes de las categorías ponderadas y no intervienen en la calificación. Desde CLASES-03 (DOCS-04), "Trabajo de clase" se llama "Actividades de aprendizaje" y el muro, "Avisos"; los temas organizan también los recursos (P-05, decisión del humano, 2026-10-26), y en "Recursos de aprendizaje" mover de tema es solo del admin: ahí la regla del bloque gana a "mover organiza la clase".
- Clases (decisión del humano, 2026-10-02; CLASES-02): solo el admin crea clases y edita su nombre y descripción, y asigna de uno a dos maestros por clase (`maestros_de_clase`), que agrega, quita o reasigna en cualquier momento; una clase nunca queda sin maestro. El maestro no crea ni edita clases; "Crear clase" desaparece de su inicio. Inscriben alumnos el admin y los maestros de la clase (alta manual y baja, registradas en `movimientos_inscripcion`); el código de invitación se conserva.
- Autoría (regla general: publicaciones, comentarios y tareas): cada autor borra solo lo suyo; un maestro nunca borra ni edita lo del admin; el admin borra cualquier publicación o comentario de cualquier clase. Un maestro borra además los comentarios de los alumnos de sus clases (moderación), nunca lo del otro maestro (P-01 de CLASES-02). La regla vive en `core/autoria.ts` (`puedeBorrar`) y se aplica dentro de la transacción del borrado; las listas devuelven `puedeBorrar` por elemento. Borrar una publicación borra también su hilo de comentarios, de quien sea (O-05 de CLASES-02b; revisar si el admin llega a comentar). Lo que publica el admin se firma "Administración", con distintivo visible y sin nombre de persona; la firma se deriva del rol del autor, no se guarda. En las tareas, cada autor edita y borra la suya; el admin edita solo las suyas y borra cualquiera; un maestro nunca edita ni borra la del admin ni la de otro maestro de la clase, salvo que ese maestro ya no dé la clase (P-04 de TAREAS-01). Una tarea con entregas solo la borra el admin, con confirmación (ENTREGAS-01). Las respuestas de tareas devuelven `puedeEditar` y `puedeBorrar`. Desde CLASES-03 (DOCS-04) la regla cubre los recursos y las dudas (viñetas siguientes), y desde FORO-01, el planteamiento de un foro, como una tarea.
- Secciones de la clase (DOCS-04; CLASES-03): siete, en este orden: Avisos · Actividades de aprendizaje · Foro · Recursos · Dudas · Personas · Calificaciones. "Avisos" reemplaza al muro y solo lleva anuncios del admin y de los maestros, con sus comentarios; las tareas pasan a "Actividades de aprendizaje" y los materiales a "Recursos". "Personas" está en los tres roles y reúne el roster del maestro y los alumnos y maestros del admin (P-01); "Foro" llega con FORO-01, en tercera posición, y CLASES-03 no la muestra vacía (P-02). Decisiones del humano, 2026-10-26.
- Recursos (DOCS-04; CLASES-03): los materiales de la clase, en dos bloques, guardados con el bloque del autor al publicar (CLASES-03a). "Recursos de aprendizaje": solo el admin sube, edita, borra y mueve. "Recursos del docente": cada maestro sube los suyos, los maestros de la clase los ven, cada autor edita y borra lo suyo y el admin borra cualquiera. Los alumnos inscritos ven los dos bloques (P-03) y los recursos conservan los comentarios de los materiales (P-06); decisiones del humano, 2026-10-26. Editar un recurso reemplaza lo guardado: lleva `version` (regla de edición concurrente). Los materiales existentes se reparten por el rol del autor en la migración. Grabaciones: pendiente de ENVIVO. Con clases vinculadas (DOCS-05; RF-76), la vinculada recibe los recursos de aprendizaje de su clase de origen, no los del docente; la forma (una publicación visible en las dos o copias sincronizadas) y de quién son los comentarios, por confirmar en ENVIVO. Los temas se gestionan en "Actividades de aprendizaje"; en "Recursos" solo se mueve un recurso. Borrar una publicación toma primero su fila y después descarta sus archivos, para quedar en serie con editar, comentar y mover.
- Dudas (DOCS-04; CLASES-03): un hilo abierto de la clase; preguntan y responden los inscritos (y los maestros de la clase), todos lo leen, no se califica. Los maestros de la clase y el admin marcan "resuelta" y borran lo de los alumnos; entre maestros, la regla general de autoría. Distinto del hilo privado de una tarea, que no cambia. El admin lee, marca "resuelta" y borra, sin escribir; cada autor borra lo suyo; solo texto, sin adjuntos ni edición; "resuelta" se puede quitar (P-07, decisión del humano, 2026-10-26). Responder toma la duda `FOR SHARE` y borrarla la toma `FOR UPDATE` antes de borrar, así quedan en serie; quién marcó «Resuelta» no sale en las respuestas (CLASES-03b).
- Foro (DOCS-04; FORO-01): una actividad calificable con los campos de una tarea (fecha límite, puntos, rúbrica opcional, tardías, categoría, tema). Previsto, no decidido (lo confirma o lo cambia el plan de FORO-01): que reutilice la fila de `tareas` y la de `entregas` por alumno para el estado y la calificación. "La entrega es participar": entregó quien publicó su participación principal; tarde y cierre como en las entregas. El alumno publica una participación principal y réplicas libres. Lo califica un maestro de la clase; el admin no califica.
- Clases archivadas, borradas y duplicadas (DOCS-04; hecho en ADMIN-01): solo el admin. Archivar es reversible y no borra nada; la clase sale de las listas de maestros y alumnos y el alumno ve sus calificaciones en "Clases anteriores". Una clase archivada es de solo lectura para todos: el maestro la consulta sin escribir, el código de invitación no sirve y sus recordatorios no avisan (P-08, decisión del humano, 2026-10-26). En ADMIN-01: archivar o restaurar responden `409 CLASE_YA_ARCHIVADA` o `409 CLASE_NO_ARCHIVADA` si la clase ya está en ese estado, sin escribir, y archivar no cancela los recordatorios (sus consumidores, que llegan con NOTIFICACIONES, terminan sin avisar). `GET /clases/anteriores` da a cada alumno y maestro sus archivadas: el alumno ve solo el detalle de la clase y "Mis calificaciones" (sin el desglose de la rúbrica ni la devolución, recorte aceptado por el humano); el maestro abre la clase en su vista de siempre, sin controles de escritura; el admin la lee completa y la gestiona. Unirse con el código de una archivada responde como un código inexistente (`404 CODIGO_INVALIDO`): unirse toma la clase `FOR SHARE` y decide dentro de su transacción. La interfaz no pinta los controles de escritura en una archivada y muestra un aviso fijo. Borrar definitivamente solo una archivada, con confirmación explícita y el conteo de alumnos, actividades, entregas, calificaciones y archivos; los objetos del almacén se borran por la cola, nunca en la petición. Duplicar copia nombre (editable), descripción, recursos de aprendizaje, secciones (los temas, con nombre y orden) y categorías ponderadas, nunca maestros, alumnos, avisos, actividades, recursos del docente ni calificaciones; como una clase nunca queda sin maestro, el admin elige de uno a dos al duplicar; se duplica también una archivada y la copia nace activa (P-10 y DE-03, decisiones del humano, 2026-10-26). Con clases vinculadas (DOCS-05; RN-12), el objetivo del cliente es que archivar o borrar definitivamente una clase no deje a su vinculada sin lo que ya recibió; cómo, lo fija ENVIVO, y el conteo del borrado definitivo tendrá que distinguir lo que se borra de lo que se conserva.
- Exportar calificaciones (DOCS-04; CALIFICACIONES-02): .xlsx de alumnos × actividades con categorías y promedio, para los maestros de la clase y el admin, desde las mismas consultas agregadas del gradebook. El archivo identifica al alumno por nombre y correo y **nunca** lleva el estado de pago ni la restricción, porque un archivo descargado sale del control de la plataforma (P-13). La API devuelve JSON y el navegador arma el .xlsx (R-01; "Archivos"). Decisiones del humano, 2026-10-26. La ruta es `GET /clases/:claseId/calificaciones/exportacion` (maestros de la clase y admin): ventanas de hasta 100 alumnos y 100 actividades, cada una en una sola instantánea y con la misma lectura del gradebook (`leerGradebookCon`); el navegador las recorre y no arma el archivo si detecta que la clase cambió entre dos ventanas (riesgo residual R-02 de CALIFICACIONES-02).
- Exámenes (DOCS-04; hito 3): pendientes por confirmar, sin planear. Sus medidas disuaden y registran; no impiden capturas ni otro dispositivo, y no se graba video.
- "Personas" del alumno (CLASES-02): correo completo de los maestros y de los compañeros de la clase. El buscador global del maestro conserva el enmascarado.
- Código de clase: 7 caracteres sin I, O, 0 ni 1; se escribe sin distinguir mayúsculas y admite como separadores los espacios y guiones de una lista cerrada; regenerarlo invalida el anterior sin afectar a los inscritos. Unirse es idempotente.
- Alta manual: el buscador del maestro muestra el nombre y el correo enmascarado (hasta 2 caracteres de la parte local y nunca todos, `***` y el dominio), enmascarado en el backend; el correo completo solo en el roster, de alumnos ya inscritos en su clase, y para el alumno en "Personas" (CLASES-02). Cada alta manual y cada baja efectivas, del maestro o del admin, se registran en `movimientos_inscripcion` en la misma transacción, ordenadas por `secuencia`, con quién lo hizo en `maestro_id` (`actorId` en el código); el admin los consulta en `/admin/movimientos` (`GET /admin/movimientos-inscripcion`, de lo más reciente a lo más antiguo, sin filtros; ADMIN-01). El buscador del admin en una clase también enmascara.

## Operación
- PostgreSQL **nunca** expuesto a internet. Puertos 80/443 del Droplet solo desde los rangos de Cloudflare.
- CORS de origen exacto `https://campus.<dominio>`, con credenciales.
- Secretos solo en `.env` del servidor. `.env.example` versionado, sin valores reales.
- Logs JSON con `requestId` y `userId`, sin contraseñas, tokens ni datos de pago. Las líneas de cada petición registran la ruta sin la cadena de consulta (`serializers.req` de `config/logger.ts`, ADMIN-01e): un filtro como `estadoPago=deudor` o un nombre o un correo escritos en un buscador no quedan en el log.
- Respaldo diario cifrado fuera del servidor, con restauración probada. `GET /api/salud` para el monitoreo.
- Las imágenes se construyen en GitHub Actions, no en el servidor. Despliegue a `prod` siempre aprobado por un humano.
- Errores de API: `{ "error": { "codigo", "mensaje" } }`.
