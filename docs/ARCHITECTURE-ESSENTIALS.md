# ARCHITECTURE-ESSENTIALS

> Solo decisiones y reglas. Detalle y justificación en `ARCHITECTURE.md`; producto en `PRD.md`.
> Si algo aquí contradice a otro documento, **manda este** y se avisa al humano.

## Qué es
**CMEP Campus Digital.** Plataforma educativa web, una sola institución, 3 roles (`estudiante`, `maestro`, `admin`). **Fase experimental**, ~1,500 usuarios previstos; la arquitectura se diseña para 2,000 simultáneos. Sin integraciones con Google.

## Proveedores
- **Sin AWS.** Ni servicios ni librerías. La regla aplica a servicios y a librerías que nuestro código importa o ejecuta; las dependencias transitivas de herramientas de desarrollo (por ejemplo, del CLI de Prisma) se reportan, pero no bloquean.
- Aprobados: **DigitalOcean** (Droplet), **Cloudflare** (DNS, Pages, R2), **LiveKit Cloud**, **Resend** (correo). Nada más sin aprobación explícita del humano.
- Todo proveedor debe poder cambiarse por configuración. El núcleo (API, worker, PostgreSQL) corre igual en local, en el Droplet o en un servidor propio.
- **Correo solo con Resend, por API HTTPS, y solo desde `adapters/notifier`.** Nada de SMTP ni de otras librerías de correo. Fuera de `prod` jamás sale un correo real.

## Stack
- **Frontend:** React + Vite + TypeScript · Tailwind (tokens propios) · shadcn/ui reestilizado · lucide-react · sonner · React Router · TanStack Query · FullCalendar · LiveKit React → **Cloudflare Pages** (`campus.<dominio>`)
- **Backend:** Node.js LTS + Fastify + TypeScript · zod · monolito modular → **Droplet** con Docker Compose (`api.<dominio>`, tras el proxy de Cloudflare y Caddy)
- **Datos:** PostgreSQL 17 (`pg_trgm`, `unaccent`) · Prisma
- **Auth:** propia — argon2id + JWT (`jose`) + token de refresco rotativo en cookie `HttpOnly`
- **Cola y trabajos diferidos:** pg-boss
- **Archivos:** protocolo S3 con cliente `minio` → **R2** en `prod`, **MinIO** en `dev` (imágenes desde `quay.io`, sin mantenimiento; reemplazable por cualquier almacén S3 vía `STORAGE_*`)
- **Video:** LiveKit Cloud + Egress hacia R2 · `livekit-server --dev` en local
- **Operación:** pino · monitoreo de DigitalOcean · `pg_dump` cifrado hacia R2 · GitHub Actions construye y publica las imágenes
- **Pruebas:** Vitest. Backend: unitarias de `core/` y `config/`, e integración contra un PostgreSQL desechable por corrida con Testcontainers (imagen de `infra/`, `prisma migrate deploy` al iniciar); nunca `campus_dev`, una base compartida ni `prod`. Frontend: jsdom + Testing Library, sin API ni infra

## Capas del backend
```
handlers → middleware → core → (interfaces) ← adapters → librerías de infraestructura
```
- `core/`: lógica pura. Sin I/O ni librerías de infraestructura.
- `config/`: validación de las variables de entorno con zod y opciones del logger. No es `core/` ni `adapters/`.
- `adapters/`: **único** lugar que importa `@prisma/client`, `@prisma/adapter-pg`, `pg`, el cliente generado por Prisma (`adapters/db/generated/`, no versionado), `pg-boss`, `minio`, `resend`, `argon2`, `jose` o `livekit-server-sdk`. Módulos: `db`, `auth`, `storage`, `notifier`, `queue` (cola y trabajos diferidos de pg-boss, con su única instancia; no hay un módulo `scheduler` aparte, TAREAS-01), `live`. Previsto (DOCS-04): si el .xlsx de la exportación de calificaciones se escribe en el backend, su librería también se importa solo en un adaptador; dónde se genera (worker, API o navegador), módulo, librería y mecanismo los decide el plan de CALIFICACIONES-02 (dependencia nueva, con confirmación del humano; ningún servicio externo).
- `handlers/`: delgados. Un plugin de Fastify por dominio: `auth`, `usuarios`, `clases`, `tareas`, `calificaciones`, `archivos`, `notificaciones`, `calendario`, `envivo`, `publico`, `admin`.
- `workers/`: consumidores de la cola. `api` y `worker` son la misma imagen con distinto arranque.
- `shared/`: tipos y esquemas zod comunes. `infra/`: compose, Caddyfile, respaldos, despliegue.

## Autenticación
- Contraseñas con argon2id, mínimo 10 caracteres. Nunca en logs.
- Token de acceso: JWT de 15 min, solo `sub`, en memoria del navegador. **Nunca en `localStorage`.**
- Token de refresco: aleatorio, cookie `HttpOnly; Secure; SameSite=Strict`, guardado **solo como hash**, 30 días, rotación en cada uso, reutilización ⇒ se revocan todas las sesiones.
- Login: 5 intentos / 15 min por IP + correo. Mismo mensaje para usuario inexistente y contraseña incorrecta.
- El correo es el identificador de acceso y **no se verifica**: puede estar mal escrito.
- Registro público: solo estudiantes. Maestros: los da de alta el admin, por invitación individual o masiva (enlace de un solo uso por correo, 72 h; al activarlo, el maestro ve y puede corregir su nombre), o se registran con un enlace de registro que genera el admin (token aleatorio mostrado una sola vez y guardado solo como hash; vigencia de 1 a 30 días, 7 por defecto; revocable; el admin ve quién se registró con cada enlace; D-04). Admin: `npm run seed:admin`, cuenta única, sin endpoint.
- **Recuperación por correo:** enlace de un solo uso, 30 min, guardado solo como hash (`tokens_cuenta`); misma respuesta y mismo tiempo exista o no el correo; 3 solicitudes por hora; al usarlo se revocan las sesiones. La API encola siempre y el worker resuelve la cuenta (no hay recuperación para el admin); límite de 3 por hora por IP + correo en la API y por cuenta en el worker. El token del enlace se deriva de su id con una clave del servidor y viaja en el fragmento de la URL.
- **Respaldo por el admin:** contraseña temporal aleatoria mostrada **una sola vez**, guardada solo como hash, activa `debe_cambiar_contrasena` y revoca sesiones. El cambio obligatorio pide solo la contraseña nueva y su confirmación, no la temporal, y exige una sesión viva del mismo usuario (cookie de refresco); un futuro cambio voluntario desde el perfil sí pedirá la actual. El admin puede corregir un correo. La del admin: `npm run reset:admin`.

## Autorización (orden fijo, siempre en backend)
1. `authenticate` → 2. `withProfile` → 3. `withPasswordGate` → 4. `withAccess` → 5. `requireRole` → 6. `requireMembership` / `requireOwnership` → 7. handler

- Rol, restricción y banderas se leen de la base en **cada** petición; no van en el token.
- `debe_cambiar_contrasena`: solo pasa `POST /auth/cambiar-contrasena`.
- Alumno restringido: solo `GET /me` y `GET /me/estado-pago` (y `POST /auth/cambiar-contrasena` si tiene un cambio pendiente). Sin tokens de LiveKit, archivos ni grabaciones.
- Estado de pago ajeno: solo admin, o maestro de una clase del alumno. Para estudiantes el campo **se omite**.
- `requireMembership`: estudiante inscrito, cualquier maestro de la clase o el admin; `requireOwnership`: cualquier maestro de la clase (de uno a dos, en `maestros_de_clase`) o el admin; siempre sobre `:claseId`, con la misma respuesta para una clase inexistente y una ajena. El admin pasa el sexto paso en cualquier clase que exista, pero solo en las rutas cuyos `roles` lo nombran de forma explícita: en una ruta sin `roles`, el sexto paso lo niega (cerrado por defecto). La guarda de `:claseId` no tiene excepciones (CLASES-02).
- Una guarda `onRoute` no deja arrancar la API si una ruta no pública, con cualquier URL, no empieza por la cadena completa o tiene un parámetro o un comodín en sus dos primeros segmentos (CHORE-02).
- Previsto (DOCS-04; ADMIN-01, carril sensible): una clase archivada se resuelve en el sexto paso de la cadena, no en los handlers. Recomendación, pendiente por confirmar: solo lectura para todos; el maestro, como en una clase ajena; el alumno, solo sus calificaciones ("Clases anteriores"); el admin, lectura completa y restaurar.

## Reglas de datos
- Prisma **solo** en `adapters/db`.
- **Sin N+1:** ninguna consulta dentro de un ciclo.
- Toda consulta filtra por columna indexada; toda lista se pagina (máx. 100).
- SQL crudo solo parametrizado. El único SQL con texto no literal que pasa por Prisma es el de pg-boss al encolar dentro de una transacción (`ejecutorSqlDe` en `adapters/db`, único `$queryRawUnsafe`): todos sus datos viajan como parámetros y el texto solo interpola el esquema, la tabla y el nombre de la cola (constantes del código).
- Escrituras compuestas en **transacción**, incluido el encolado del evento.
- Transacciones que crean, rotan o revocan sesiones en bloque, cambian la contraseña o escriben enlaces de un usuario existente: primero su fila de `usuarios` (`FOR SHARE` para crear o rotar su sesión; `FOR NO KEY UPDATE` para lo demás), en READ COMMITTED. Protocolo en `backend/src/adapters/README.md`.
- Toda transacción se abre con `enTransaccion` (`adapters/db`). Si expira esperando un bloqueo o una conexión (`P2028`), responde `503 SERVICIO_OCUPADO`, nunca `500`.
- **Edición concurrente** (ENTREGAS-01): llevan `version` (entero, desde 0, sube en cada cambio) las filas que se editan con un formulario que reemplaza lo guardado y las decisiones que alguien toma sobre lo que vio: hoy `tareas` (editar la exige; mover de tema también la sube) y `entregas` (entregar, anular y calificar la suben; calificar la exige: si el alumno anuló o volvió a entregar, u otra persona calificó, `409 ENTREGA_MODIFICADA`). Calificar envía además los puntos de la tarea que vio (`puntosDeLaTarea`): si ya no son los de la tarea bloqueada, o la rúbrica cambió, `409 RUBRICA_MODIFICADA`; no usa `tareas.version`, que también sube al mover de tema (CALIFICACIONES-01). La petición envía la versión que vio; si no coincide con la de la fila ya bloqueada, `409` sin escribir nada. `actualizado_en` no sirve de precondición. Tras el `409`, el formulario de la tarea avisa, descarta lo escrito y recarga la versión actual, como el editor de categorías (decisión del humano, 2026-10-11). Tras un `409` al calificar (`ENTREGA_MODIFICADA`, `RUBRICA_MODIFICADA` o `ENTREGA_NO_CALIFICABLE`), el panel de calificación avisa, descarta lo escrito y recarga la entrega y, con `RUBRICA_MODIFICADA` o `ENTREGA_NO_CALIFICABLE`, también la tarea, como el formulario de la tarea; si la recarga falla, conserva lo escrito y la versión que vio (CALIFICACIONES-01). Excepciones ya decididas, sin versión: las categorías se guardan en bloque y, tras un `409` o un `404`, el editor descarta y recarga (decisión del humano, 2026-10-11); los temas se renombran y ordenan sin versión, porque no hay texto largo que perder, y el orden se renueva tras `ORDEN_DESACTUALIZADO`.
- Una lectura de varias sentencias (Prisma resuelve cada relación anidada con otra sentencia) cuya respuesta exige una relación obligatoria o una cardinalidad mínima, o que comprueba la fila del cursor antes de leer la página, se hace en una sola instantánea: `enTransaccion` con `instantaneaUnica` (REPEATABLE READ, solo lecturas). Las transacciones que escriben siguen en READ COMMITTED (FIX-CLASES).
- Promedios, gradebook, alumnos en riesgo y KPIs: **consultas agregadas**, no contadores guardados.
- Todo cambio de esquema es una migración de Prisma, **compatible hacia atrás** (frontend y backend se despliegan por separado).
- Fechas `timestamptz` en UTC; ISO 8601 en la API.
- Tablas y columnas en `snake_case` español; `camelCase` en TypeScript vía `@map`. Llaves UUID.
- Búsqueda de alumnos: `nombre_busqueda` se normaliza en `core/` al escribir (sin acentos, minúsculas, espacios colapsados) y se busca con `LIKE` y el índice GIN de trigramas sobre esa columna; el término pasa por la misma normalización, definida una sola vez en `shared/`, y escapa los comodines. Mide de 3 a 120 caracteres ya normalizados, con un tope de 1000 en crudo. `unaccent` no se usa en las consultas. Frontend: espera de 300 ms.

**Previsto (DOCS-04), sin migrar; cada encargo lo confirma en su plan:** `publicaciones.tipo` suma `foro` (FORO-01), con su fila 1:1 en `tareas` como la tarea · `publicaciones.bloque` (`aprendizaje` / `docente`) y `publicaciones.version` para los recursos (CLASES-03) · tabla `dudas`, con sus respuestas en `comentarios` como tercer contexto (`duda_id`) (CLASES-03) · tabla `participaciones_foro` (principal y réplicas; FORO-01) · `clases.archivada_en`, con `clases.activa`, que hoy existe sin uso (ADMIN-01). La exportación .xlsx no lleva tabla.

Restricciones clave: `email` único · un solo `rol = 'admin'` (índice único parcial) · `maestros_de_clase (clase_id, maestro_id)` PK, de uno a dos por clase, validado en `core/` dentro de la transacción, con la fila de la clase bloqueada (CLASES-02) · `entregas (tarea_id, alumno_id)` único · `notificaciones (usuario_id, evento_id)` único · `comentarios` con exactamente un contexto: `publicacion_id` (muro) o `entrega_id` (hilo privado; ENTREGAS-01) · `archivos`: confirmado si y solo si tiene exactamente un contexto (`publicacion_id` o `entrega_id`; los `pendiente` y `descartado`, ninguno; `clase_id` autoriza mientras tanto) · `entregas`: una fila por alumno y tarea, creada al primer uso (entregar, comentar o calificar); `asignado` sin `fecha_entrega`, `entregado` con ella, y `calificado` con `calificacion` y `fecha_calificacion`, con o sin `fecha_entrega` (sin ella cuando se calificó a quien no entregó); sin `fecha_entrega` no hay retraso ni enlaces. "Entregó" es tener `fecha_entrega`, no el estado (ENTREGAS-01; CALIFICACIONES-01) · `puntajes_rubrica (entrega_id, criterio_id)` PK, el desglose de una calificación con rúbrica; su FK a `criterios_rubrica` es `NO ACTION DEFERRABLE INITIALLY DEFERRED` (se comprueba al confirmar) y está escrita a mano en la migración, porque Prisma no la expresa (CALIFICACIONES-01) · `categorias.peso` de 1 a 100, con la suma de 100 por clase validada en `core/` con la fila de la clase bloqueada · `publicaciones.tema_id` con `ON DELETE SET NULL`; un anuncio no lleva tema (TAREAS-01) · una tarea es una publicación de tipo `tarea` con su fila 1:1 en `tareas` (mismo id; TAREAS-01).

## Asíncrono y notificaciones
- La API guarda y encola **en la misma transacción**, y responde. **Nunca** crea notificaciones en la petición.
- Todo aviso y todo correo sale por `adapters/notifier`: `avisar(destinatarios, aviso)` y `correoDeCuenta(...)`. Nadie más escribe en `notificaciones` ni llama a Resend.
- **Aviso = notificación in-app siempre + correo solo si ese tipo está activado** en `configuracion` (todos apagados por defecto; los enciende el admin).
- **Correos de cuenta** (recuperación, invitación de maestro): siempre activos, solo por correo, con prioridad en la cola. La invitación masiva se rechaza completa si rebasa el cupo `INVITACIONES_LIMITE_DIARIO` (80 invitaciones en las últimas 24 h; Resend gratuito: 100 correos por día UTC) y encola un trabajo por maestro en su misma transacción; el worker deja al menos 250 ms entre dos intentos de envío.
- Un correo por destinatario, con límite de ritmo. Canal `registro` en `dev` y pruebas.
- Idempotencia por `eventId`. 3 reintentos con espera exponencial; después, cola de fallidos vigilada.
- Eventos: `PUBLICACION_CREADA` · `MATERIAL_CREADO` · `TAREA_CREADA` · `ENTREGA_REALIZADA` · `CALIFICACION_PUBLICADA` · `COMENTARIO_CREADO` · `RECORDATORIO_24H` · `CLASE_POR_COMENZAR` · `CORREO_DE_CUENTA` · `ENVIAR_CORREO` · `GRABACION_LISTA` · `LIMPIEZA_DIARIA` · `RESPALDO_DIARIO`. `ENTREGA_REALIZADA` lleva `{ entregaId, tareaId, claseId, version }` con un id nuevo por entrega; `COMENTARIO_CREADO` sirve al muro y al hilo privado (ENTREGAS-01). `CALIFICACION_PUBLICADA` lleva `{ entregaId, tareaId, claseId, version }` con un id nuevo por publicación (también al recalificar) y cubre el comentario de la devolución, que no encola `COMENTARIO_CREADO` (CALIFICACIONES-01). DOCS-04 no agrega eventos: los avisos de "Dudas" y del foro están pendientes por confirmar y los decide NOTIFICACIONES; los recursos siguen con `MATERIAL_CREADO` y los anuncios de "Avisos" con `PUBLICACION_CREADA`.
- Frontend: sondeo cada 60 s + al enfocar la pestaña. Sin WebSockets. Contador = `COUNT` sobre índice parcial de no leídas. Retención de 90 días.

## Trabajos diferidos
- Uno por tarea (`fecha_limite − 24 h`) y uno por clase en vivo (`fecha_inicio − 15 min`). Desde FORO-01, uno por actividad con fecha límite: tarea o foro (DOCS-04).
- Guardar `trabajo_id`. **Editar o borrar la fecha ⇒ cancelar y recrear, en la misma transacción.**

## Archivos
- Subida y descarga con URL prefirmada de 5 min. Los archivos **nunca** pasan por Node ni por el Droplet.
- Registro `pendiente` → `confirmado`; los pendientes de más de 24 h se borran.
- Buckets: `campus-privado` (`materiales/` · `entregas/` · `grabaciones/`) · `campus-publico` (`anuncios/`) · `campus-respaldos` (solo en `prod`; en `dev` MinIO crea únicamente los dos primeros).
- Tokens de mínimo privilegio: aplicación, Egress (solo escritura en `grabaciones/`), respaldos.
- Cambiar de almacén = cambiar `STORAGE_ENDPOINT`, `STORAGE_ACCESS_KEY`, `STORAGE_SECRET_KEY`.
- Materiales, anuncios y adjuntos de tareas: solo los sube un maestro de la clase o el admin (CLASES-02); 25 MB por archivo, 5 por publicación o tarea; PDF, imágenes (sin SVG), Office y texto plano. La confirmación compara el objeto real con lo declarado, dentro de la transacción de la publicación. Vista previa solo de imágenes. La limpieza borra también el objeto de los pendientes vencidos y de los descartados.
- Entregas (ENTREGAS-01): el alumno sube los archivos de su entrega por su propia ruta (`…/tareas/:tareaId/entrega/archivos`, solo mientras puede entregar), con clave `entregas/{tareaId}/{alumnoId}/{archivoId}`; mismos tipos, 25 MB por archivo y 5 por entrega, más hasta 5 enlaces `http`/`https`. Un archivo de entrega solo se descarga por sus rutas (el alumno, los suyos; los maestros de la clase y el admin, los de sus alumnos inscritos); la descarga de la clase solo sirve archivos de publicaciones, y la confirmación de una publicación o de una entrega exige el prefijo de su clave. Anular pasa los archivos a `descartado`.
- Previsto (DOCS-04): los recursos (CLASES-03) usan los archivos de los materiales, sin cambio; los adjuntos del planteamiento de un foro, los de una tarea (FORO-01). La exportación .xlsx (CALIFICACIONES-02) y los objetos de una clase borrada o duplicada (ADMIN-01) siguen esta sección: nada pasa por Node en una petición; si el plan de CALIFICACIONES-02 propone responder el archivo desde la API, es un apartamiento de esta regla y lo decide el humano.
- Sin las tres `STORAGE_*` de acceso, la API arranca y los archivos responden 503; en `production` son obligatorias (API y worker). Firmar es local: la región es fija (`STORAGE_REGION`).

## Reglas de negocio que tocan código
- Estado de pago: `Deudor` / `Al corriente`. Por defecto `Al corriente`. Manual, solo admin. Guarda fecha de cambio. **No bloquea nada por sí solo.**
- Restricción de acceso: independiente del estado de pago. Solo admin, solo estudiantes, efecto inmediato, reversible.
- Calificación (RF-36, RN-05; CALIFICACIONES-01): un maestro de la clase califica una entrega con la rúbrica (la suma de los puntos por criterio, escalada a los puntos de la tarea y redondeada a centésimas) o, sin rúbrica, con una calificación directa, con hasta 2 decimales. Publicar es devolver: el alumno la ve en cuanto se guarda, y el comentario opcional de la devolución va al hilo privado de la entrega, sin aviso propio (P-01 y P-02). Recalificar vuelve a publicar. A quien no entregó solo se le califica con la entrega cerrada, es decir, con la fecha límite vencida en una tarea que no acepta entregas con retraso (P-03 c′): la fila queda `calificado` sin `fecha_entrega`, el alumno ya no entrega ni anula, y no cuenta entre los que entregaron. Una tarea con alguna entrega calificada no cambia sus puntos ni su rúbrica (`409 TAREA_CON_CALIFICACIONES`), y una rúbrica idéntica nunca se reemplaza (P-04). El admin lee las calificaciones y no califica (S-01). Calificación general: por categorías ponderadas y, dentro de cada una, por puntos (P-05); las categorías sin tareas calificadas no cuentan y su peso se reparte; las tareas sin calificar no cuentan; las entregas con retraso cuentan igual. Desde FORO-01, el foro es una actividad calificable más: se califica por alumno con las mismas reglas y pondera en su categoría (DOCS-04).
- Categorías ponderadas (RF-32; P-01 de TAREAS-01): hasta 10 por clase, sin nombres repetidos (misma comparación que los temas), con pesos enteros de 1 a 100 que suman 100; se guardan en bloque y las gestionan los maestros de la clase y el admin. Una clase sin categorías califica por puntos; con categorías, toda tarea nueva o editada lleva una, y una tarea "Sin categoría" no cuenta en la calificación general hasta asignarle una. No se quita una categoría que tiene tareas.
- Alumno en riesgo: promedio < 70 % o ≥ 3 tareas vencidas sin entregar. Los umbrales son constantes de `core/` hasta que exista la configuración (RF-56), y el promedio que se compara es el redondeado que se muestra. "Vencidas sin entregar" son las tareas de la clase con la fecha límite pasada y sin entrega `entregado` ni `calificado` del alumno: una calificada sin entrega no cuenta, porque su calificación ya pesa en el promedio. Cuentan también las que vencieron antes de que el alumno se inscribiera, como en "Trabajo de clase" (S-04) (CALIFICACIONES-01). Desde FORO-01 cuentan las actividades: un foro vencido sin participación principal del alumno es una vencida sin entregar (DOCS-04).
- Entregas (RF-14, RF-15, RF-24, RF-44; ENTREGAS-01): el alumno entrega una vez, con archivos y enlaces o, si la tarea no requiere adjuntos (`requiere_adjuntos`, lo decide el maestro), con "Marcar como completada"; anula y vuelve a entregar mientras no esté calificada. Tarde es después de la fecha límite: si la tarea acepta tardías, la entrega se marca `con_retraso` al entregarla; si no, se cierra en la fecha límite y ya no se entrega ni se anula. El cierre se calcula en cada acción con la tarea vigente: mover la fecha límite o aceptar tardías la reabre. Borrar una tarea con entregas (S-06, decisión del humano del 2026-10-11): un maestro no la borra (`409 TAREA_CON_ENTREGAS` con el conteo; lo pide a administración); el admin sí, con una confirmación explícita (`?confirmar=entregas`), en cascada e irreversible: se lleva las entregas, sus archivos y los hilos privados. Cuentan las entregas `entregado` y `calificado`. Hilo privado (RF-16; ENTREGAS-01): uno por alumno y tarea, entre el alumno y los maestros de la clase; el admin lo lee y no escribe; en esta fase sus comentarios no se borran ni se editan.
- Temas (RF-43; P-03 de CLASES-01 y P-02 de TAREAS-01): organizan las tareas y los materiales de una clase, con nombre y orden (hasta 30 por clase, sin nombres repetidos: se comparan con `claveDeNombre` de `shared/src/tareas.ts`, sin distinguir mayúsculas, acentos, caracteres invisibles ni formas de compatibilidad). Un elemento puede quedar "Sin tema"; dentro de un tema van del más reciente al más antiguo; borrar un tema pasa sus elementos a "Sin tema". Los gestionan los maestros de la clase y el admin; mover un elemento de tema organiza la clase y no cuenta como editarlo. El alumno ve "Trabajo de clase" agrupado y de solo lectura, y el muro sigue cronológico. Son independientes de las categorías ponderadas y no intervienen en la calificación. Desde CLASES-03 (DOCS-04), "Trabajo de clase" se llama "Actividades de aprendizaje" y el muro, "Avisos"; si los temas siguen organizando los recursos está pendiente por confirmar, y en "Recursos de aprendizaje" mover de tema es solo del admin: ahí la regla del bloque gana a "mover organiza la clase".
- Clases (decisión del humano, 2026-10-02; CLASES-02): solo el admin crea clases y edita su nombre y descripción, y asigna de uno a dos maestros por clase (`maestros_de_clase`), que agrega, quita o reasigna en cualquier momento; una clase nunca queda sin maestro. El maestro no crea ni edita clases; "Crear clase" desaparece de su inicio. Inscriben alumnos el admin y los maestros de la clase (alta manual y baja, registradas en `movimientos_inscripcion`); el código de invitación se conserva.
- Autoría (regla general: publicaciones, comentarios y tareas): cada autor borra solo lo suyo; un maestro nunca borra ni edita lo del admin; el admin borra cualquier publicación o comentario de cualquier clase. Un maestro borra además los comentarios de los alumnos de sus clases (moderación), nunca lo del otro maestro (P-01 de CLASES-02). La regla vive en `core/autoria.ts` (`puedeBorrar`) y se aplica dentro de la transacción del borrado; las listas devuelven `puedeBorrar` por elemento. Borrar una publicación borra también su hilo de comentarios, de quien sea (O-05 de CLASES-02b; revisar si el admin llega a comentar). Lo que publica el admin se firma "Administración", con distintivo visible y sin nombre de persona; la firma se deriva del rol del autor, no se guarda. En las tareas, cada autor edita y borra la suya; el admin edita solo las suyas y borra cualquiera; un maestro nunca edita ni borra la del admin ni la de otro maestro de la clase, salvo que ese maestro ya no dé la clase (P-04 de TAREAS-01). Una tarea con entregas solo la borra el admin, con confirmación (ENTREGAS-01). Las respuestas de tareas devuelven `puedeEditar` y `puedeBorrar`. Desde CLASES-03 (DOCS-04) la regla cubre los recursos y las dudas (viñetas siguientes), y desde FORO-01, el planteamiento de un foro, como una tarea.
- Secciones de la clase (DOCS-04; CLASES-03): siete, en este orden: Avisos · Actividades de aprendizaje · Foro · Recursos · Dudas · Personas · Calificaciones. "Avisos" reemplaza al muro y solo lleva anuncios del admin y de los maestros, con sus comentarios; las tareas pasan a "Actividades de aprendizaje" y los materiales a "Recursos". Pendiente por confirmar: si "Personas" reúne el roster del maestro y los alumnos y maestros del admin, y si "Foro" llega con FORO-01.
- Recursos (DOCS-04; CLASES-03): los materiales de la clase, en dos bloques, guardados con el bloque del autor al publicar (recomendación; decide CLASES-03). "Recursos de aprendizaje": solo el admin sube, edita, borra y mueve. "Recursos del docente": cada maestro sube los suyos, los maestros de la clase los ven, cada autor edita y borra lo suyo y el admin borra cualquiera. Editar un recurso reemplaza lo guardado: lleva `version` (regla de edición concurrente). Los materiales existentes se reparten por el rol del autor en la migración. Grabaciones: pendiente de ENVIVO.
- Dudas (DOCS-04; CLASES-03): un hilo abierto de la clase; preguntan y responden los inscritos (y los maestros de la clase), todos lo leen, no se califica. Los maestros de la clase y el admin marcan "resuelta" y borran lo de los alumnos; entre maestros, la regla general de autoría. Distinto del hilo privado de una tarea, que no cambia. Pendiente por confirmar: si el admin escribe, si cada autor borra lo suyo, solo texto y sin edición.
- Foro (DOCS-04; FORO-01): una actividad calificable con los campos de una tarea (fecha límite, puntos, rúbrica opcional, tardías, categoría, tema). Previsto, no decidido (lo confirma o lo cambia el plan de FORO-01): que reutilice la fila de `tareas` y la de `entregas` por alumno para el estado y la calificación. "La entrega es participar": entregó quien publicó su participación principal; tarde y cierre como en las entregas. El alumno publica una participación principal y réplicas libres. Lo califica un maestro de la clase; el admin no califica.
- Clases archivadas, borradas y duplicadas (DOCS-04; ADMIN-01): solo el admin. Archivar es reversible y no borra nada; la clase sale de las listas de maestros y alumnos y el alumno ve sus calificaciones en "Clases anteriores". Borrar definitivamente solo una archivada, con confirmación explícita y el conteo de alumnos, actividades, entregas, calificaciones y archivos; los objetos del almacén se borran por la cola, nunca en la petición. Duplicar copia nombre, descripción, recursos de aprendizaje y secciones (recomendación, pendiente por confirmar: los temas), nunca maestros, alumnos, avisos, actividades, recursos del docente ni calificaciones; como una clase nunca queda sin maestro, el admin elige de uno a dos al duplicar (pendiente por confirmar).
- Exportar calificaciones (DOCS-04; CALIFICACIONES-02): .xlsx de alumnos × actividades con categorías y promedio, para los maestros de la clase y el admin, desde las mismas consultas agregadas del gradebook. Pendiente por confirmar: qué identifica al alumno y si se excluyen el estado de pago y la restricción (recomendación: excluirlos, porque un archivo descargado sale del control de la plataforma; el correo, solo si el colegio lo necesita). Mecanismo en su plan (Archivos).
- Exámenes (DOCS-04; hito 3): pendientes por confirmar, sin planear. Sus medidas disuaden y registran; no impiden capturas ni otro dispositivo, y no se graba video.
- "Personas" del alumno (CLASES-02): correo completo de los maestros y de los compañeros de la clase. El buscador global del maestro conserva el enmascarado.
- Código de clase: 7 caracteres sin I, O, 0 ni 1; se escribe sin distinguir mayúsculas y admite como separadores los espacios y guiones de una lista cerrada; regenerarlo invalida el anterior sin afectar a los inscritos. Unirse es idempotente.
- Alta manual: el buscador del maestro muestra el nombre y el correo enmascarado (hasta 2 caracteres de la parte local y nunca todos, `***` y el dominio), enmascarado en el backend; el correo completo solo en el roster, de alumnos ya inscritos en su clase, y para el alumno en "Personas" (CLASES-02). Cada alta manual y cada baja efectivas, del maestro o del admin, se registran en `movimientos_inscripcion` en la misma transacción, ordenadas por `secuencia`, con quién lo hizo en `maestro_id` (`actorId` en el código); la consulta es de ADMIN. El buscador del admin en una clase también enmascara.

## Operación
- PostgreSQL **nunca** expuesto a internet. Puertos 80/443 del Droplet solo desde los rangos de Cloudflare.
- CORS de origen exacto `https://campus.<dominio>`, con credenciales.
- Secretos solo en `.env` del servidor. `.env.example` versionado, sin valores reales.
- Logs JSON con `requestId` y `userId`, sin contraseñas, tokens ni datos de pago.
- Respaldo diario cifrado fuera del servidor, con restauración probada. `GET /api/salud` para el monitoreo.
- Las imágenes se construyen en GitHub Actions, no en el servidor. Despliegue a `prod` siempre aprobado por un humano.
- Errores de API: `{ "error": { "codigo", "mensaje" } }`.
